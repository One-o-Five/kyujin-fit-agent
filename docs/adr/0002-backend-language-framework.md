# バックエンドを TypeScript + Hono で実装し、評価スクリプトのみ Python を許可する

## 背景と課題

APIサーバーと分析ワーカーの実装言語・フレームワークを決める必要がある。LLMの呼び出しは外部APIで行い、モデルの学習は行わない。業務ではJava（Spring系）を使用しており、レイヤー設計の経験がある。

## 判断基準

* **フロントエンドとの型・スキーマ共有**: 一人でフルスタックを開発するため、React + TypeScript との間で型を共有し、仕様の食い違いを防ぎたい。
* **起動の速さとメモリ使用量**: 分析ワーカーをLambdaで動かす可能性がある（[アーキテクチャ](../architecture.md)の未決定事項）。
* **入力検証・API仕様書・LLM出力検証の一元化**: 同じスキーマから生成したい。
* **新しい技術領域の習得**: 業務と同じ技術では、個人開発で示せる内容が少ない。

## 検討した選択肢

言語:

* Java / Spring Boot
* Python / FastAPI
* TypeScript

フレームワーク（TypeScript）:

* NestJS
* Hono

## 決定

選択肢: **TypeScript + Hono**。判断基準をすべて満たし、Honoが構造を強制しない点は業務で培ったレイヤー設計で補えるため。

1. APIサーバーと分析ワーカーは TypeScript + Hono で実装する。
2. スキーマはZodで定義し、`packages/shared` でフロントエンドと共有する。入力検証、OpenAPIドキュメント、LLM出力の検証（[ADR-0001](0001-analysis-result-storage.md)）に同じ仕組みを使う。
3. 評価スクリプト（`evals/`）に限りPythonを許可する。

### 影響

* 良い点: フロントとAPIで型を共有し、API変更時の不整合をコンパイル時に検出できる。
* 良い点: Node.js / Lambda の両方で同じコードが動き、ワーカーの実行基盤を後から選べる。
* 悪い点: レイヤー構成を自分で維持する必要がある。Lintルールとディレクトリ構成で依存方向を守る。
* 悪い点: 言語が2つになるため、CIではTypeScriptとPythonのジョブを分けて実行する。

### 確認方法

* Lintルールで `routes` → `services` → `repositories` 以外の方向の import を禁止し、CIで検査する。
* `packages/shared` のスキーマを変更した際に、APIとフロントの両方で型チェックが通ることをCIで確認する。

## 各選択肢の長所と短所

### Java / Spring Boot

* 良い点: 業務と同じ技術で最も早く作れる。
* 悪い点: メモリ使用量が多く、Lambdaではコールドスタートが不利。
* 悪い点: フロントと型を共有できない。

### Python / FastAPI

* 良い点: AI・データ分析のライブラリが最も豊富。
* 悪い点: 本サービスはLLMをAPI経由で呼ぶだけで、その利点が活きにくい。
* 悪い点: フロントと型を共有できない。

### TypeScript + NestJS

* 良い点: DI・モジュール構成がSpringに近く、構造が標準で揃う。
* 悪い点: ボイラープレートが多く重い。Lambdaでのコールドスタートが不利。

### TypeScript + Hono

* 良い点: 軽量・高速。Web標準APIベースで Node.js / Lambda の両方で同じコードが動く。
* 良い点: Zodと連携し、入力検証とOpenAPIドキュメントを同じスキーマから生成できる。
* 悪い点: 構造を強制しないため、レイヤー分割や依存関係の管理を自分で設計する必要がある。

## 補足

### レイヤー構成

```
routes/        HTTPの入出力のみ（リクエストの検証、レスポンスの整形）
services/      ビジネスロジック（利用量制限、結果の再利用判定など）
repositories/  DBアクセス
lib/           LLMクライアント、キュー、外部サービスのラッパー
```

* `routes` → `services` → `repositories` の方向にのみ依存する。
* 外部サービス（DB、LLM、SQS）は `services` からインターフェース経由で利用し、テストで差し替えられるようにする。

### 評価スクリプトにPythonを許可する理由

* 評価は集計・可視化が中心で、Pythonのデータ分析ライブラリが適している。
* 評価スクリプトは本番のリクエストを処理しない独立した用途のため、言語を分けても運用の負担が小さい。
* 評価対象のデータ（LLM出力の原本、プロンプトのバージョン）はDBとファイルを介して受け渡し、サービスのコードには依存しない。

### 再検討の条件

将来チーム開発に移行し、構造の統一がより重要になった場合は、NestJSへの移行を再検討する。
