# 認証にサーバーセッションと HttpOnly Cookie を使う

## 背景と課題

本サービスは招待コード制の会員登録を行い、ユーザーごとに職務経歴書と分析結果を管理する。職務経歴書は個人情報を含むため、認証の安全性を重視して認証方式を決める必要がある。

フロントエンド（React SPA）とAPIは、CloudFrontで同一ドメインに配置する（`/` → S3、`/api/*` → ALB → ECS）。

## 判断基準

* **即時の無効化**: ログアウトやパスワード変更時に、発行済みの認証情報をすぐに無効にしたい。
* **XSSへの耐性**: 認証情報をJavaScriptから読めない場所に置きたい。
* **運用の単純さとコスト**: 個人開発のため、構成要素と固定費を小さく抑えたい。

## 検討した選択肢

* A. セッション + HttpOnly Cookie
* B. JWT（アクセストークン + リフレッシュトークン）

## 決定

選択肢: **A. セッション + HttpOnly Cookie**。同一ドメイン構成のSPAであり、複数サービス間での認証連携も不要なため、JWTの利点が活きない。即時無効化のしやすさと実装の単純さを優先する。

### 影響

* 良い点: パスワード変更時に `user_id` 単位でセッションを削除し、全端末を強制ログアウトできる。
* 良い点: セッションの保存先を既存のPostgreSQLにすることで、構成要素が増えない。
* 悪い点: CSRF対策が必要になる。
* 悪い点: 期限切れセッションを定期的に削除する処理が必要になる。

### 確認方法

* 統合テストで、ログアウト後・パスワード変更後に旧セッションCookieでのアクセスが 401 になることを確認する。
* 異なる `Origin` からの状態変更リクエストが拒否されることを確認する。

## 各選択肢の長所と短所

### A. セッション + HttpOnly Cookie

* 良い点: サーバー側でセッションを削除すれば即時に無効化できる。
* 良い点: CookieはJavaScriptから読めないため、XSS発生時もトークンを盗まれにくい。
* 悪い点: セッションの保存先が必要。
* 悪い点: CSRF対策が必要。

### B. JWT

* 良い点: サーバーがセッション状態を持たなくてよい。
* 良い点: 複数サービス・モバイルアプリとの連携に向く。
* 悪い点: 有効期限前のトークンを無効化するにはブラックリスト等が別途必要で、結局サーバー側に状態を持つことになる。
* 悪い点: ブラウザでの保存場所を慎重に選ぶ必要がある（localStorageはXSSに弱い）。

## 補足

### 実装方針

| 項目 | 方針 |
|---|---|
| セッションID | 暗号論的乱数で256bitを生成。DBにはSHA-256ハッシュのみ保存（DB流出時に流用されないため） |
| 保存先 | PostgreSQLの `sessions` テーブル。Redisは使わない（下記） |
| Cookie属性 | `HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/` |
| 有効期限 | 7日。アクセスのたびに延長（スライディング方式） |
| CSRF対策 | `SameSite=Lax` に加え、状態を変更するリクエストでは `Origin` ヘッダーを検証 |
| パスワード | Argon2idでハッシュ化 |
| ブルートフォース対策 | ログインAPIにIP・メールアドレス単位の試行回数制限 |
| ログアウト | セッション行を削除し、Cookieを失効させる |

```sql
CREATE TABLE sessions (
  id_hash      TEXT PRIMARY KEY,
  user_id      BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  expires_at   TIMESTAMPTZ NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_sessions_user ON sessions (user_id);
```

### Redisを使わない理由

想定ユーザー数（招待制で数十人規模）ではPostgreSQLで十分な性能が出る。ElastiCacheを追加すると固定費と構成要素が増えるため、現時点では採用しない。

### 再検討の条件

* モバイルアプリや外部連携が必要になった場合は、トークン方式の併用を検討する。
* ユーザー数が増えてセッション参照がDB負荷のボトルネックになった場合は、Redisへの移行を検討する。
