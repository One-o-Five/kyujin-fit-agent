# フロントエンドを SPA（React + Vite）で構成し、静的ホスティングで配信する

## 背景と課題

フロントエンドの構成方式を決める必要がある。本サービスはログイン後にのみ利用するサービスで、検索エンジンに公開するページはほぼない。APIは TypeScript + Hono で別サービスとして構築する（[ADR-0002](0002-backend-language-framework.md)）。

## 判断基準

* **SEO・初回表示速度の必要性**: ログイン後の画面が中心で、要求は低い。
* **運用対象とコスト**: 個人開発のため、画面用サーバーを持たずに済ませたい。
* **APIとの責務分担**: APIはすでに分離しており、画面側にサーバーロジックを持たせたくない。
* **同一ドメイン配信**: CloudFrontで `/` を画面、`/api/*` をAPIに振り分ける（[アーキテクチャ](../architecture.md)）。

## 検討した選択肢

* A. SPA（React + Vite）
* B. Next.js（SSR / React Server Components）

## 決定

選択肢: **A. SPA（React + Vite）**。SSR・SEOの利点が小さく、APIはすでに分離している。静的ホスティングによるコストの低さと構成の単純さを優先する。

| 項目 | 方針 |
|---|---|
| ビルド | Vite + React + TypeScript |
| 配信 | S3 + CloudFront |
| 型・スキーマ | `packages/shared` のZodスキーマをAPIと共有する |

### 影響

* 良い点: 画面用サーバーを持たないため、フロントエンドの運用コストはS3とCloudFrontの利用料のみとなる。
* 良い点: 画面とAPIの責務が明確に分かれる。
* 悪い点: SPAのルーティングのため、CloudFrontで存在しないパスに `index.html` を返す設定が必要。
* 悪い点: 公開ページでSEOやOGPが必要になった場合は別途対応が必要。

### 確認方法

* デプロイ後、`/analyses/42` のような画面のURLを直接開いても表示されること（404にならないこと）を確認する。

## 各選択肢の長所と短所

### A. SPA（React + Vite）

* 良い点: ビルド結果が静的ファイルのみで、S3 + CloudFrontに置くだけで配信できる。
* 良い点: 構成が単純。
* 悪い点: 初回表示時にJavaScriptの読み込みが必要。
* 悪い点: SEOやOGP（SNSでのプレビュー）には向かない。

### B. Next.js

* 良い点: サーバー側で描画するため初回表示が速く、SEOに強い。
* 良い点: 求人での採用例が多い。
* 悪い点: SSRを使うにはNode.jsの実行環境が必要で、運用対象とコストが増える。
* 悪い点: API RoutesやServer ActionsがHonoのAPIと役割が重なり、ロジックの置き場所の判断が増える。

## 補足

* データ取得（分析状態のポーリングなど）、状態管理、スタイリングの方式は、P1で実装しながら決め、必要に応じてADRを追加する。
* 公開ページ（サービス紹介、利用規約など）でSEOやOGPが必要になった場合は、その部分のみ静的生成で対応する、またはNext.jsへの移行を改めて検討する。
